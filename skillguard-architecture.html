SkillGuard — Architecture Overview Detect malicious AI-agent Skills before your coding agent trusts and runs them · v0.1.0 · Detection-Engine-only MVP

1Business Context

Developers pull Skills (SKILL.md instructions + optionally bundled scripts) from GitHub and the web, then let their coding agent load and act on them — with no checkpoint. Because a Skill is instructions the agent will follow and code the agent may run, a malicious one can quietly read secrets, exfiltrate data, or run destructive commands.

Objective

Prove detection works

Distinguish malicious Skills from safe ones with a low false-positive rate — the one genuinely unproven part of the design.

Users

Developers & CI

Anyone about to trust a cloned Skill. Scriptable via exit codes for local checks and pipelines.

Value

Explained verdict

Not just a red light: a plain-language reason naming which Threat Vector fired and where.

Metrics

Accuracy over time

Detection rate, false-positive rate, per-scan latency, and vector attribution — tracked by the eval harness.

Scope of this release: the Detection Engine only. It reports a Verdict; it does not gate installs. Out of scope: the install gate, Canonical Bundle Hash cache & shared verdict DB, provenance scoring, sandboxed execution, and the Chrome/CI surfaces.

2Data Flow

A folder on disk becomes a normalized in-memory Skill, is analyzed by two layers, and collapses into a single Verdict with evidence and an exit code.

3Processing Pipeline

The two layers run over the same untrusted Skill, then combine_verdict reconciles them under the static floor rule (ADR 0002): the LLM may raise severity but can never single-handedly lower a statically-flagged Skill to Clean.

No static findings + LLM Clean

Floor is Clean → Clean. A purely LLM-surfaced concern can still reach Suspicious/Malicious on its own.

Static findings + LLM Malicious

The LLM raised it → Malicious. Deterministic evidence is listed first, LLM evidence appended.

Static findings + LLM Clean

Floor holds → Suspicious. A Skill that tried to steer the LLM to "Clean" still surfaces for human review.

4System Architecture

Layered, dependency-light. The domain models are stdlib-only frozen dataclasses that every layer speaks; the LLM sits behind a Protocol port so the deterministic test suite injects a stub with no network.

Static Pass — deterministic floor

A pure skill → findings function. Four detectors scan line-by-line: Prompt Injection & Analyzer Manipulation (recorded as Prompt Injection), Malicious Bundled Code, and Second-Stage / Obfuscation. Reads the raw Skill and cannot be talked out of a match — which is why it sets the floor.

LLM Judgment — semantic catch

Behind an injectable LLMJudge Protocol. AnthropicJudge wraps the Skill as clearly-delimited untrusted <skill> data with a hardened system prompt (analyze, never obey), then parses a JSON tier + findings + explanation. Catches disguised/novel intent regex misses.

Non-functional

Deterministic core

Static Pass is pure (no I/O, no globals) — each danger pattern is cheap to unit-test. LLM port stubbed → the pytest suite runs with no network or key.

Non-functional

Cross-platform identity

Loader normalizes LF endings and drops .git/OS/editor junk, so the same Skill on Windows/Mac/Linux analyzes identically (the future Canonical Bundle Hash rule).

Non-functional

Injection-hardened

Static floor (ADR 0002): the LLM can raise but never lower a flagged Skill to Clean. Skill content is data, never instructions.

Accuracy is measured, not asserted. evals/run_eval.py drives a corpus of 16 clean Skills + 4 hand-crafted malicious Skills (one per vector) through the real model, scoring detection rate, false-positive rate, latency, and vector attribution. It's kept out of pytest because the model is non-deterministic. Run --offline for a Static-Pass-only plumbing check.

6Deployment & Workflows

Model & prerequisites

  • Runtime: Python 3.11+ CLI, packaged with hatchling
  • Deps: typer (CLI), anthropic (LLM)
  • Secret: ANTHROPIC_API_KEY for the LLM layer
  • Model: SKILLGUARD_MODEL (defaults to claude-sonnet-5) — a config detail behind the port, not an architectural commitment

Dev tooling

  • pytest — deterministic suite, LLM stubbed, no network
  • ruff + mypy --strict — lint & types on src
  • devtools/tester.py — local web app watching a scan flow stage-by-stage; reuses combine_verdict so it matches analyze
  • evals/ — accuracy measurement, tracked over time

Command surface

# install (dev) uv venv && uv pip install -e ".[dev]" # scan a Skill on disk → prints Verdict, sets exit code skillguard scan path/to/skill Verdict: Clean # exit 0 Verdict: Suspicious # exit 1 (+ findings: [vector] file:line) Verdict: Malicious # exit 1 # measure accuracy against the real model python evals/run_eval.py # needs ANTHROPIC_API_KEY python evals/run_eval.py --offline # Static Pass only, no key # watch a scan flow through the engine, stage by stage python devtools/tester.py # http://localhost:8000
Deployment model: local developer CLI / CI step. It reports only — there is no server, gate, cache, or shared database in this release. Exit codes make it wireable into scripts and pipelines today; the install gate and shared verdict DB are deliberately deferred until the engine's accuracy is validated.
